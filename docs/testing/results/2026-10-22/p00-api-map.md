# P00 live REST API map

Date: 2026-10-22
Scope: read-only code, local migrations, and auth/config mapping for the profile UAT in [`2026-10-22-live-test-user-profiles.md`](../2026-10-22-live-test-user-profiles.md). No remote database calls, account creation, data changes, deployment, or credentials were used in this mapping.

## Live REST harness

The app uses Supabase Auth password grant, then sends each PostgREST RPC as `POST /rest/v1/rpc/<function>` with JSON arguments. For an isolated session per profile:

1. Use the development project's `VITE_SUPABASE_URL` and publishable/anon key from the approved local configuration, without copying either value into the result log.
2. Authenticate that profile with `POST {SUPABASE_URL}/auth/v1/token?grant_type=password`, headers `apikey: <publishable-or-anon-key>` and `Content-Type: application/json`, body `{"email":"<profile-email>","password":"<entered-at-runtime>"}`.
3. Keep the returned access token in that profile's session only. Invoke RPCs with `apikey: <publishable-or-anon-key>`, `Authorization: Bearer <profile-access-token>`, and JSON `Content-Type`. Send `Accept-Profile: public` if using the app's configured schema behavior; omit profile-specific headers for the default `public` schema.
4. Capture only HTTP status, safe response fields/IDs, and before/after business state. Never log the password, access/refresh token, anon key, service-role key, or full Auth response.

The local client confirms this header behavior in `src/lib/supabase.ts`; `src/features/auth/api/auth.api.ts` uses the password grant. The UI persists one token under browser localStorage key `auth-storage`, so browser-based profile runs need separate browser profiles or a cleared/logged-out session between identities. The login form takes an email, not the proposed `uat.*` username.

## Auth and setup findings

- Repo config exposes only a browser publishable/anon key to the REST/Auth clients. `.env.development.local` contains configuration keys for Supabase, login domain, and database URL; values were deliberately not read or included here. `src/config/env.ts` consumes `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, and schema, while the auth session is persisted client-side.
- `supabase/README.md` documents initial admin bootstrap as: create an Auth user in the development project, then assign the `system_admin` role to its Auth UUID. Migration `20261010020000_seed_initial_system_admin_account.sql` seeds the role/permission setup, not a reusable plaintext login. No test usernames or passwords are committed in the profile document.
- Account creation in the UI requires a deployed `account-management` Edge Function and its `SUPABASE_LOGIN_DOMAIN` secret. The local env file has a `VITE_SUPABASE_LOGIN_DOMAIN` key, but current `src/config/env.ts` does not consume that key; browser login itself submits a full email. Verify Edge Function deployment/secret state before relying on UI account creation. This does not block logging into accounts provisioned by another approved method.
- The latest local scope migration is `20261022033339_eps_accounts_external_organizations_and_permission_scopes.sql`; `20261022033509_revoke_role_permission_trigger_execute.sql` further removes direct execute on the role-scope trigger. The receipt API is defined in `20261021052315_material_receipts_and_warehouses.sql`; latest migration replaces scoped list/detail RPCs for materials, handovers and receipts. A remote migration check was intentionally outside this read-only mapping, so local code contracts are not a statement that the dev project is already at that schema version.
- P00's required pre-existing admin session/credential cannot be established from repository code. README provides the initialization route, but an existing Auth account and assigned role must be confirmed through the authorized dev project/session before P00 can prepare profiles. Do not infer admin status from an account name or frontend permission state; verify actual `user_roles`/effective grants.
- Profile document proposes role names and scope assignments; live setup should resolve each role UUID and inspect the permission catalog first. Scope enum values in the migration are `team`, `department`, `all`, and `assigned_warehouses`; no row/grant is the `none` case. Database scope checks use linked `user_profiles` identity and mock EPS organization links, not account display names.
